Running a task again when it completes

By default, a task waits for its schedule: when an execution ends, the next one starts at the task's next firing. A task that works a queue, such as one that implements issues one at a time, can instead fire again as soon as an execution completes, so that it takes its next item without waiting. This is the task's completion policy. This page says how to set it, which executions run again, and where the runs again stop.

Setting the policy

In the task editor, the task's Schedule section holds the policy and its limit:

  • When an execution completes. Wait for the schedule, the default, or Run again.
  • Run-again limit. How many runs again may follow, in a row, the execution that started them: a whole number from 1, 10 by default. You can change it only while Run again is chosen.

Saving the task writes both to the task's file, and you can also set them there; see A task is a file. In the file, the completion block under spec holds them as policy, wait_for_schedule or run_again, and runAgainLimit.

A task that only runs a script has no completion policy, and its editor does not show these fields.

Which executions run again

With the policy set to run_again, an execution that ends as completed fires the task again at once, whatever fired it: its schedule, a catch-up, a run you started by hand, or an earlier run again. The new execution is queued and started like any other.

Only a completed execution runs again. An execution that found no work, failed, was cancelled, needs your attention, or was interrupted does not: the task waits for its schedule. An execution that completed with a draft pull request whose tests failed is still completed, so it runs again.

The task as it is when the execution ends

HarmFlow reads the policy when the execution ends, from the task's definition at that moment, not from the one the execution started with. So the execution does not run again when, in the meantime, the task was disabled, deleted, set back to wait_for_schedule, or its file became invalid. Nor does it run again while HarmFlow is stopping.

A firing that was already waiting

If a firing of the task was already waiting in the queue when the execution completed, such as one of its schedule that came due while it ran, the run again joins it: the two become one execution, which keeps the trigger of the firing that waited. The count of runs again goes on from the execution that completed.

Where the runs again stop

Runs again in a row stop at the task's limit. With the default of 10, one firing gives at most 11 executions in a row: the one that started the sequence and 10 runs again. The execution that completes at the limit starts no other, and the task waits for its schedule.

HarmFlow then tells you, with a Run-again limit reached notice, that the task ran again that many times in a row and now waits for its schedule. The notice comes even when the task notifies you of no event; only a Notification level of None in Settings holds it back.

The count starts again from zero at the task's next firing after the limit, and after a sequence that ends with any result other than completed.

Seeing a run again

An execution that a run again started shows Run again as its trigger, in the History screen's Trigger column, and in the queue while it waits. Its detail, in the History and Executions screens, also shows Follows and the ID of the execution whose completion started it: select it to open that execution. The app's local API also records how many runs again in a row it is.
