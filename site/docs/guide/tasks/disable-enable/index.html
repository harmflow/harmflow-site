Disabling and enabling a task

A disabled task keeps its file, its settings, and its history, but HarmFlow starts nothing for it until you enable it again. This page says what disabling stops, what happens to a run already in progress, how enabling picks the schedule up again, and what becomes of a task that cites an agent or a skill its AI tool does not have.

How to disable or enable a task

On the Tasks screen, each task's row has a switch beside Run now. It reads Enabled or Disabled; click it to change the task's state. A disabled task's row is dimmed, shows no next run, and its Run now button is greyed out.

A client of the local API does the same with POST /tasks/{taskId}/disable and POST /tasks/{taskId}/enable.

The change is written to the task's file

Either way, HarmFlow writes the change to the task's file at once: it sets the task's enabled field and leaves the rest of the file as it was, its comments included. The state lasts across restarts of the app, and a task file you open afterwards shows it.

What disabling stops

Disabling stops every new firing of the task:

  • A firing that comes due while the task is disabled does not start. HarmFlow records it in the record of the task's firings as skipped, with the reason that the task was disabled.
  • A firing already waiting in the queue, behind an execution of the task that runs, is cancelled and never starts. Its execution ends as cancelled, with the reason that the task was disabled.
  • A manual run is refused. The Tasks screen greys out Run now, and the local API answers a request to run the task with an error that says it is disabled and must be enabled to run.

A run already in progress

An execution that is running when you disable the task is not stopped: it finishes normally, with the result it would have had. Disabling only keeps new ones from starting. To stop a run at once, cancel the execution itself.

Enabling the task again

Once enabled, the task follows its schedule from where it is now. Its next firing starts on time, at the next occurrence its schedule gives, as a normal firing on schedule. There is no catch-up: none of the firings skipped while the task was disabled runs afterwards.

For example, a made-up task Weekly digest fires every Monday at 09:00. You disable it one Friday and enable it again eleven days later, on a Tuesday. The two Monday firings in between were skipped and recorded as such; the task's next firing is the following Monday at 09:00, and nothing runs on the day you enable it.

A task whose agents or skills are missing

A task may cite an agent or a skill that its AI tool does not have on this Mac. Saving such a task only warns, and it is disabled and enabled like any other task:

  • The change shows no error. The switch on the task's row, and the local API, do not check the task's agents and skills again, so the missing ones never block the change.
  • It keeps its warnings. The task keeps one warning for each missing agent or skill, the ones it had before the change. The task list shows them before and after the change: a chip on the task's row counts them, such as 2 warnings, and pointing at it lists each one, such as Agent not found or Skill not found with the item's name.
  • It keeps its parameter values. The values the task gives a missing agent's or skill's parameters stay in its file, unchanged.
