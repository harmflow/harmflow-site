An execution that ran out of quota

When the harness running an execution runs out of quota, HarmFlow carries the execution on to the next harness the task names. When no harness is left to take over, the execution ends as Out of quota, not as Failed. Running out of quota is expected, not something that went wrong: the execution sends no failure notice, is not listed among the executions that need your attention, and waits for the task's next scheduled run.

For example, a task named Nightly triage runs on Claude Code, with Codex as its fallback. Claude Code runs out of quota halfway through, and the execution switches to Codex, whose quota then runs out too. No harness is left, so the execution ends Out of quota.

When an execution ends Out of quota

An execution ends Out of quota when its last attempt ended on quota and no other harness can take over: the task names none, or the execution already made every switch the task allows. An attempt ends on quota in any of these ways:

  • its harness's plan quota was already exhausted before the attempt, so no session started;
  • the share of the harness's quota you let HarmFlow spend was already reached before the attempt, so no session started either;
  • the quota ran out during the session;
  • a Claude Code session turned to extra usage, which the task does not allow, so HarmFlow ended it.

The two checks before an attempt run only while the task does not allow extra usage, as a new task does not. Ending on quota leads to Out of quota only when the task fails over on quota: its fallback's Quota exhausted trigger, which a new task has on. A task with that trigger off stops at the first quota that runs out, and its execution ends Failed.

When it reads Needs attention instead

When the session had already reported a pull request before the quota ran out, the execution ends Needs attention instead: a pull request waits for you to take on. A branch the session pushed without opening a pull request is not looked for, so that execution still ends Out of quota, and a later execution of the work item can carry that branch on. An execution where a work item opened no pull request explains the other cases where an execution reads Needs attention or Failed.

Endings that still read Failed

Every other ending with no harness left still ends Failed. A last harness that is unavailable is one of them, even when an earlier harness of the same execution ran out of quota.

Executions that ended before HarmFlow had the Out of quota status keep the Failed status they ended with: nothing changes them.

Notices

An execution that ends Out of quota sends no failure notice: neither Operational failure nor No alternative AI tool fires for it, though a new task notifies about both.

A task may choose to be told: check Out of quota under Notify me about, in the task's Notifications section. A new task leaves it unchecked. It is not a failure, so its notice goes through only at the All notification level: Failures and attention only holds it back.

The Overview and History

The Needs your attention panel of the Overview does not list an execution that ran out of quota: nothing went wrong in it.

The Out of quota today card counts the executions that ended Out of quota since midnight, apart from Failed today: such an execution counts in its own card, never as a failure. The Overview and the Executions screen show the card by default, at the end of the cards you already arranged. To hide or show it on either screen, open Settings, then Appearance, and use Metric cards; a change applies the next time the screen opens.

The History screen shows the execution's status as Out of quota, and its Status filter offers Out of quota, so you can list those executions alone. In the execution's Events tab, its ending reads No AI tool had quota left.

The next run

An execution that ran out of quota does not run again at once, even for a task that runs again after a completed execution: it waits for the task's schedule. The work items it selected and left without a result stay in progress and count no failure toward the task's limit of retries, so a later execution takes them up again.
