An execution where a work item opened no pull request

A task that works items such as issues delivers each one as a pull request. When the session ends, its report gives the result of each work item it worked. A work item that failed before its pull request was opened delivered nothing, so HarmFlow reads the execution by what happened to each item's pull request, not only by the outcome the report states.

Failed or Needs attention

  • Every work item of the report failed with no pull request. The execution ends as Failed, whatever outcome its report states. A report of one work item reads the same way: when that one item failed with no pull request, the execution failed.
  • Only some of several work items failed with no pull request. The execution ends as Needs attention, not Completed. It ends as Failed only when the session's own report says the execution failed.

Only a work item the report gives as failed counts here. An item it gives as skipped, as handed to you, or as closed is not one of the items that opened no pull request, even though it has none.

A draft pull request whose tests fail still counts as an opened pull request: its work item delivered a draft that documents the failing tests, so it is not one of the items that opened no pull request.

An execution can also read Needs attention when HarmFlow could not use its report at all: An execution whose report was ignored explains that case.

Reading the reason

The execution's reason names each work item that failed with no pull request, by its repository and its number, in the order of the report. For a report of one work item, it reads, for example, the pull request of owner/repo#12 was not opened. For a report of several, it lists every such item, separated by commas: no pull request was opened for owner/repo#12, owner/repo#15.

The reason is shown in the app's language: English, Portuguese, or Spanish.

What is kept for each item

Each work item that failed with no pull request counts one failure toward the task's limit of retries. It keeps its branch and its worktree, the folder in the task's workspace where its work was done, so you can see what the session left there.

The clean-up keeps that worktree until the item ends, such as when its issue is closed, or until the execution's log expires: after a failed execution, the worktree goes once its log expires, and after one that needs attention, it stays until the item ends. An execution whose log has expired explains what the log's expiry leaves behind.
